1. [context_compliance / T-68-13, plans 68-12 and 68-10] The new parenthetical 'FSB never reads what you typed into them' (and the variants in the 68-12 truths, the 68-10 copy facts, VALIDATION AUTO-01-c and M-68-09) is false. FSB's LLM snapshot reads `node.value` for inputs and textareas (formatInlineRef, extension/content/dom-analysis.js:~2215). Fast mode's own hand-off snapshot (requestSnapshot -> getMarkdownSnapshot) also sends those values to the user's AI provider. The privacy page's existing Data Collection and External Services units already say FSB inspects the DOM. Scope the claim to fast mode, for example 'fast mode leaves them out when it describes the page'. Add `/FSB never reads/i` to FORBIDDEN_PATTERNS. Fix this before 68-10 runs: afterwards the fix means another extract and re-translation in six locales.

2. [truthfulness D-10/D-18, T-68-04, plans 68-04 Task 2, 68-05 Task 2 and 68-06 Task 3] classifyStepEvidence maps every success:false result with result===null and an error to 'denied'. SW-side dispatch failures have exactly that shape: makeResult({success:false, error:'Content tool click failed: <msg>'}) (extension/ai/tool-executor.js:~163), for example when the message channel closes because a link click navigated, and 'Tab was closed or became inaccessible' (:~157). The hand-off then says the step was not permitted, when the true wording is 'may have executed; inspect the page before retrying'. Treat null-response failures as 'uncertain' unless they are positively identified as a permission denial, and add a case for a channel-closed error.

4. [context_compliance D-17, plans 68-04 and 68-05] D-17 says an unchanged page signature across fast steps escalates and latches the command, with a hint. isNoProgress returns false after any observed effect, so a verified click that leaves url and signature unchanged only gets a 'same_state' decline: no command latch and no stuck hint in the hand-off. Either latch with reason no_progress when an acted step leaves url+signature unchanged, or record this as a deliberate deviation in the 68-05 SUMMARY and the AUTO-04-c row.

5. [verification harness, plan 68-06 Tasks 2/3 and 68-07] The harness runs every non-iteration setTimeout callback on the next microtask. The fake-gateway client from makeClient(responder, opts) is created without setTimeoutImpl, so FsbJevClient's decide deadline fires almost at once and aborts the fake fetch, giving timeout or aborted results. The accepted-step, budget and stop cases would then fail for harness reasons. In the harness, pass setTimeoutImpl/clearTimeoutImpl to makeClient, or defer timers with a delay above 0 until they are cleared or advanced.

6. [robustness, plan 68-05 step p] A local buildRequest {ok:false, reason:'invalid_request'} goes through classifyFallback and latches the whole session. One example: every menu entry is dropped (checked boxes, password, hidden, file or vault fields) while only scroll is offered, so 'target' has zero elements and fails the 67 validator. That is a property of the page, not a gateway mismatch. Decline 'nothing_offerable' when no element would remain, or treat a local invalid_request as a command latch.
