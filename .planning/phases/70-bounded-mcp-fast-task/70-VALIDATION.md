# Phase 70 — Validation Strategy

> Per-phase validation contract for feedback sampling during execution.
> Sources: `70-RESEARCH.md` → `## Validation Architecture`, `## Verified Findings That Change or Sharpen the Plan` (F1-F18), `## Common Pitfalls` (1-12), `## Open Questions (RESOLVED)` and `## Security Domain`; `70-CONTEXT.md` D-01 (switch-off proof), D-02 (success-criteria split and deferral), D-05 (inverted 68 tests), D-20 (additivity proof), D-24 (sync re-check) and D-25 (test, tripwire and commit rules), plus `<deferred>`.
> Requirement: MCP-03 (owned). MCP-04 (byte-stable wire for existing callers) is guarded here but owned by Phase 69. Planning baseline: `e1e6439c` (detached planning worktree `the repository root`). Phases 66.1 and 69 are executing in the main tree, 67 is next and 68 follows, so none of their code (`FsbFastPath`, `fsbFastModeSessionField`, `FsbJevState`, `FsbJevClient`, `FsbJevPolicy`, `tests/fixtures/agent-loop-fast-harness.js`, `tests/fixtures/jev-fake-gateway.js`, `tests/helpers/mcp-in-process.mjs`, `tests/mcp-tools-list-shape-freeze.test.js`, `tests/fixtures/jev-fast-disclosure-facts.js`) is in this worktree. Every name below is quoted from their PLANs and is re-checked against the real code by 70-01 before any Phase 70 source edit (D-24).
> Task IDs: each row's Task ID column names its `70-NN-MM` task(s) from the eight Phase 70 plans, followed in parentheses by the original requirement-scoped key (`MCP-03-x`, `ALL-x`). The key stays as the row alias that the success-criterion table and plan 70-08 cite (for example "row ALL-a"). The split is one plan per wave: 70-01 sync re-check, sweep baseline, tripwire and switch-off golden (wave 1); 70-02 gate widening, D-05 inversions and the `run_task` budget profile (wave 2); 70-03 evidence recorder (wave 3); 70-04 goal normaliser and disclosure re-verify (wave 4); 70-05 classifier and end-to-end loop outcomes (wave 5); 70-06 bridge block and wire outcomes (wave 6); 70-07 in-process caller and bench record (wave 7); 70-08 phase gate (wave 8). Plans run one per wave, as in Phase 68: `parallelization` is on and `use_worktrees` is off, so same-wave plans would share one working tree, and sweeps and full-chain runs are not safe under concurrent executors.
> Validation deferral policy (STATE.md → "v1.0.0-specific decisions", owner direction 2026-10-15; CONTEXT D-02): every Phase 70 plan is `autonomous: true` and has no `checkpoint:*` task. Anything that needs the operator, a live account, a real MCP host, production, real spend or a human eye is listed under "Manual-Only Verifications" with its V-id and is deferred to the milestone-end Validation Block (V1 baseline at `8a058bdf`; V2 Jev gateway deploy; V3 shadow calibration; V4 comparative gate; V5 human UAT; V6 release, publish and merge). Fast mode stays default-off. Under the shipped `UNCALIBRATED` profile the live loop never acts (67 D-28, 68 D-02), so the acting `run_task` path is proven only with the 68 fake gateway and a test-only calibrated result (68 D-21). No test reaches `full-selfbrowsing.com` or any upstream, and no test binds 7225 or 7226.

## Sampling Rate

- **After every task commit:**
  - Run the task's `<automated>` command on Node 24. It holds only the task's own new or extended suites, the 70-01 tripwire, `node tests/delegation-phase-contract.test.js` where the task edits the test chain or the bridge (D-20), the three run_task bridge suites for a bridge edit (D-01), and the task's grep gates.
  - Source-pin preflight (CONTEXT D-25): before editing `background.js`, `mcp-bridge-client.js`, `jev-fast-path.js`, `run-bench.mjs` or any test, grep `tests/` for `.match(`, `.includes(`, `indexOf(`, `readFileSync` and `sha256(` pins on that file; bump paired pins in the same commit and run each suite the grep names before committing. The full pin bundle for each edited file (table below) runs at the wave check.
  - Whenever `package.json` or the test chain changes: `node tests/delegation-phase-contract.test.js`.
- **After every plan wave:**
  - The regression sweep over every file edited in the wave against `70-SWEEP-BASELINE.json` (in the background, waited for).
  - The wave check in the plan's `<verification>`: the pin bundle for every file edited in the wave (table below) and the Node 20 runs (`npx --offline -y node@20`) of every suite created or extended in the wave. A failure is fixed in a `fix(70-NN)` commit that names the task commit it completes, never by weakening a pin or a case.
  - `npm run validate:extension` after waves 2, 3 and 6, the waves that edit `extension/background.js` or `extension/ws/mcp-bridge-client.js` (the wave check in the `<verification>` of 70-02, 70-03 and 70-06).
  - Every `tests/jev-*` suite present (67's, 68's and 70's), `node tests/jev-policy-tighten-only.test.js`, `node tests/jev-run-task-upstream-contract.test.js`, and the bridge goldens `node tests/run-task-fast-mode-wire.test.js`.
  - From wave 7 (70-07-01 creates the caller suite): `npm --prefix mcp run build && node --test tests/mcp-run-task-fast-caller.test.mjs && node tests/mcp-tools-list-shape-freeze.test.js`, then `git status --porcelain -- mcp/` must print nothing.
- **Before `/gsd-verify-work` (phase gate, 70-08):**
  - `npm run validate:extension && npm test` is green (run in the background and waited for; it can exceed the 10-minute foreground limit; with 7225 held by the user's hub, the 67-13 tolerant per-command pass instead shows every Phase 70 command at exit 0 and no pre-existing command changing its exit code), then `npm --prefix mcp run build && node tests/mcp-tool-smoke.test.js`.

  - The three showcase crawler files are restored and not committed.

These steps are kept out of every per-task `<automated>` command and run once per wave instead, each listed as the wave check in the plan's `<verification>`: `npm run validate:extension` (after waves 2, 3 and 6), the per-file pin bundles (the background.js bundle after waves 2 and 3, the bridge reader bundle after wave 6), every Node 20 parity run (every wave), and `npm --prefix mcp run build` (wave 7, 70-07-01 step 1; the per-task caller check relies on 69's `assertBuildFresh()` and fails loudly on a stale build rather than rebuilding).
