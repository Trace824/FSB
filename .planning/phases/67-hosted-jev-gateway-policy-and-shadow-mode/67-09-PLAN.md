Router contract (this plan):
`createJevRouter({db, config, fetchImpl, now = Date.now, log = console, profiles = loadProfiles(), randomUUID = crypto.randomUUID, upstreamByteBudget = CONTRACT.BUDGETS.upstreamByteBudget})` returns an express.Router with:
- `router.post('/decide', configGate, bodyParser, handler)`; `router.all('*', ...)` -> 404 typed `invalid_request` body (so API paths never fall through to the showcase HTML); a router-local error middleware.
- Wire body, ok: `{ok:true, decisionId, instrumentVersion, servedModel, calibration:{status, profileId}, decisions, usage, cost, latencyMs}` (latencyMs = gateway latency). Fallback: `{ok:false, fallback, servedModel, httpStatus, latencyMs}` where httpStatus equals the HTTP status of this response. All responses set `Cache-Control: no-store`.
- Spend accounting (Pitfall 9): an in-memory `{dayUtc, usd}` accumulator seeded once per UTC day from `todaySpendUsd` (try/catch; on failure seed 0 and log the fixed line `[jev] spend seed failed`); for every request that reaches upstream add capUsd = the provider cost when it is greater than 0, else the estimate when it is greater than 0, else the request upper bound `bytes * config.inputUsdPerMtok / 1e6` (so every acquired request moves the accumulator by a positive amount, which bounds ledger rows per UTC day by dailyUsdCap divided by the smallest accrual); refuse with spend_cap_reached when `usd >= config.dailyUsdCap` before acquiring the semaphore.
- Ledger policy (Pitfall 13, D-08): a per-decision row exists only for requests that acquired the semaphore. After `semaphore.tryAcquire()` succeeds, the outcome is 'ok' or an upstream-stage reason (`LEDGER_OUTCOMES`), and the router calls `recordDecision(db, row, {capUsd})` with a fresh `decisionId = randomUUID()` (returned to the client only inside an ok body). Every other outcome (disabled, not_configured, body-parser rejections, the 404 catch-all, invalid_request, sensitive_goal, payload_too_large from the budget, spend_cap_reached, busy, and server_error from the outer catch or the error middleware) calls only `recordAggregateOnly(db, {dayUtc, outcome})`, which touches one bounded jev_daily row per (day, outcome). No ledger row is ever built from a body that failed validation, so `kinds`, `elementCount` and `requestBytes` always come from a validated request. Both calls sit inside try/catch with the fixed log line `[jev] ledger write failed`.
- One log line per ledger row, written only after recordDecision is attempted: `log.log(formatDecisionLog(row))`. The line starts with the row's decisionId, so the operator can find the matching row with `node src/jev/report.js --recent N` (67-05). Aggregate-only outcomes write no per-request log line.
